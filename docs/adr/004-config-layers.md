# ADR 004: 서비스 신원과 배치는 client에, 정본은 DB에 둔다

- Status: Accepted
- Date: 2026-07-03 (개정 2026-07-09: 등록부의 정본을 config에서 DB로. 2026-07-13: capacity를 관찰 기준선으로. 2026-08-26: client 소유 storage 모델 반영)
- 부모: [000](000-identity.md) 공유 전제(여러 서비스가 하나의 filegate를 쓴다), 공리 1 (소유 분리), 공리 3 (내부 의존 0)

## 문제

filegate는 여러 서비스가 쓴다 (000의 전제). 각 서비스의 신원과 인증 수단, 업로드가 향할 storage를 안정적으로 연결할 등록부가 필요하다. 이 등록은 재배포 없이 바뀌어야 하고, 실행 중인 모든 파드가 같은 정본을 봐야 한다. Terraform은 이 등록부를 선언적으로 관리하는 운영자 API 클라이언트일 수 있다.

## 결정

- **storage와 client가 등록부의 두 축이다.** storage는 물리 접근 계약이고, client는 서비스 신원이다. client는 `storage_id`로 기반 storage 하나를 직접 참조하고, 클라이언트 키와 S3 자격증명을 소유한다.
- **등록부의 정본은 DB다.** 변경은 운영자 API를 통해서만 한다 (AWS 모델). 재배포 없이 등록이 바뀐다.
- **비밀의 저장 방식은 성격이 정한다.** 클라이언트 키는 검증만 필요하므로 sha256 해시로만 저장한다. storage와 S3 자격증명 시크릿은 filegate가 서명·검증에 원문을 써야 하므로 암호화(AES-GCM, 마스터 키는 env)해 등록부에 보관한다 — opsgate의 credential 보관 방식.
- **서비스 계약은 물리 배치와 분리한다.** 네이티브 표면은 file_id, S3 호환 표면은 client id 버킷과 서비스 소유 논리키를 쓴다. `storage_id`는 운영자 등록 정보이며 서비스 파일 참조에 섞이지 않는다.
- **현재 배치는 client 등록 시 고정한다.** 운영자 API는 client 생성·조회·삭제만 제공하고 `storage_id` 갱신은 제공하지 않는다. 기존 파일을 둔 채 새 업로드만 다른 storage로 보내는 변경은 이동 정책과 갱신 계약을 정한 뒤 추가한다.
- **참조 무결성은 DB가 쓰기 시점에 집행한다.** client나 location이 참조하는 storage와 파일이 남은 client의 삭제는 거부된다. client의 키·S3 자격증명·논리키 매핑은 소유물이므로 client와 함께 삭제된다.
- **storage 등록은 그 자체가 검증이다.** 등록 요청에 담긴 자격증명으로 저장 공간 접근을 즉석 확인하고, 실패하면 등록을 거부한다.
- **capacity는 storage 등록의 일부다 — 집행이 아니라 관찰 기준선이다** ([spec 00](../spec/00-operations.md)). 시스템 기본값은 없다 — 등록자가 정하며, 무료 구간([vendors/](../vendors/README.md))이 권장 시작값이다. quota 집행은 비목표다 (관찰이 대신한다).

## 경계선

- filegate는 서비스가 정한 논리키와 메타데이터의 의미를 해석하지 않는다.
- 관리 화면은 두지 않는다. 표면은 운영자 API와 그 클라이언트다: Terraform provider(선언 관리), 필요 시 CLI.
- 운영자 API 인증은 정적 운영자 토큰(env, 쉼표 목록)이다 — 메인/서브 두 개로 무중단 로테이션한다.
- 서버(프로세스) 설정은 전부 env다. YAML 설정 파일은 두지 않는다. env의 비밀은 마스터 키·운영자 토큰·DB URL뿐이다.
- storage·client·자격증명 등록은 운영자 API로 한다. SQL 직접 변경은 지원되는 제어 표면이 아니다.

## 결과

- 기존 storage에 새 서비스를 온보딩하려면 client와 필요한 자격증명을 등록한다 (`terraform apply` 또는 같은 API를 쓰는 클라이언트). 재배포는 없다.
- DB가 런타임 정본이다. Terraform 선언은 관리 대상의 복구 재료가 될 수 있지만 DB 백업을 대체하지 않는다.
- 클라이언트는 다른 클라이언트의 영역을 수정할 수 없다.
- 사용량 조회는 운영자 시점뿐이다. 클라이언트는 용량 정보를 받지 않는다 — 자기 사용량 관리가 필요한 서비스는 스스로 한다 (공리 1).
