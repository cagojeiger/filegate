# spec 04: 집행

- Status: Accepted
- Date: 2026-07-25
- 근거: ADR [000](../adr/000-identity.md) (결정·집행 분리), [001](../adr/001-multi-storage.md) (storage는 데이터)

요청 경로 밖의 일을 누가·몇 개나 실행하는지 정한다. 판단은 클러스터에
하나고, 집행은 파드마다 여럿이다.

## 평면 셋

작업은 질문 둘로 배치된다.

```
클라이언트가 응답을 기다리는가?  ─예→  ① 요청 경로
                                └아니오→  저장소 백엔드 I/O가 있는가?
                                              ├아니오→  ② reconciler
                                              └예────→  ③ 워커
```

| | ① 요청 경로 | ② reconciler | ③ 워커 |
|---|---|---|---|
| 개수 | 파드당 무제한 | **클러스터 1** | **파드당 N** |
| 배타성 | 없음 | advisory lock | 큐 행 claim |
| 파드를 늘리면 | 용량 ↑ | 그대로 1 | **용량 ↑ (파드×N)** |
| 만지는 것 | DB + (중계 시) 바이트 | **DB만** | 저장소 객체 |
| 실패하면 | 클라이언트에 에러 | 다음 회차 | 재큐 + backoff |

- **①**: create · commit · stat · delete 결정 · 서명 발급 · 중계 바이트.
  바이트를 만져도 여기 남는다 — 클라이언트가 지금 스트리밍 중이라 미룰 수
  없다. 자원 한도는 스풀 슬롯이 따로 다스린다.
- **②**: 상태에서 집행 대상을 도출해 큐에 넣고, claim 만료를 회수하고,
  보존 정리·스냅샷을 돌린다. 바이트를 만지지 않으므로 회차가 밀리초에
  끝나고 락을 오래 쥐지 않는다.
- **③**: observe · reclaim · purge. 큐에서 집어 집행한다.

파드 로컬 OS temp의 크래시 스풀만 예외로 큐 밖·락 밖에서 모든 파드가
직접 치운다 — 자기 디스크는 자기 몫이고, 락 승자만 치우면 나머지 파드의
잔여물이 밀린다.

## 큐 — 배타성의 단위를 바꾸는 장치

락은 파드 하나를 고를 뿐 작업을 나누지 못한다. 파드를 늘려 집행 용량을
늘리려면 "이 일은 내가 집었다"를 적을 자리가 있어야 한다. 그 자리가 큐의
행이다.

```
queued ──claim(SKIP LOCKED)──▶ active ──집행 완료──▶ 행 삭제
   ▲                              │
   │                              └─ 실패 ─▶ queued (attempts++, backoff)
   └── claim 만료 (파드 죽음) ─────┘
```

- **종착 상태가 없다.** 상태에서 파생된 일은 잘못된 요청이 아니라 항상
  유효하고, 실패는 저장소·네트워크의 일시 장애다. 버리지 않고 간격만
  벌려 재시도하며, 누적 시도 횟수가 곧 "막혔다"는 신호다 (자가점검의 STUCK).
- **claim은 짧은 트랜잭션 하나다.** 집행이 아무리 길어도 커넥션을 쥐지
  않는다. 대신 `claimed_at`이 회수의 근거다.
- **파일 행이 사라지면 그 작업도 사라진다** (FK CASCADE) — 파일 정리가
  큐의 존재를 알 필요가 없다.

## 불변식 넷

| # | 불변식 | 무엇을 막나 |
|---|---|---|
| 1 | 요청 경로는 큐에 넣지 않는다 — 넣는 쪽은 상태다 | enqueue 누락으로 일이 영영 안 되는 것 |
| 2 | reconciler는 바이트를 만지지 않는다 | 락 보유가 길어져 판단이 밀리는 것 |
| 3 | 한 작업은 통째로 집행된다 (사슬을 쪼개지 않는다) | 전이와 실물 조작이 갈라지는 것 |
| 4 | 정합성은 조건부 전이가 보장한다 | 큐·워커가 정합성 책임을 지는 것 |

불변식 1이 level-triggered의 견고함이다: 어떤 이유로 큐가 비어도 다음
회차가 같은 상태를 보고 다시 넣는다. 불변식 3 때문에 종료 시 워커는 집던
작업을 끝내고 나온다 — 강제 종료로 끊긴 것은 claim 만료가 되돌린다.

집행자는 스냅샷이 아니라 **집행 시점의 상태**를 본다. 도출은 대상 id만
남기고, 집행 직전에 재료를 다시 읽어 조건에서 빠졌으면 건너뛴다. 도출과
집행은 큐를 거치며 벌어지고 다른 파드에서 일어나므로, 이 재조회가 낡은
재료로 실물을 건드리지 않게 하는 유일한 장치다.

## 작업 갈래

순서가 갈래마다 다르다. 각 단계가 실패해도 앞 단계의 상태는 유효하다.

| 갈래 | 대상 | 순서 | 왜 이 순서인가 |
|---|---|---|---|
| observe | lease가 살아 있는 단일 PUT pending | 관찰 → 대조 → 확정 | 실물이 선언과 맞을 때만 확정 (spec 00) |
| copy | `staging` 배치가 있는 파일 | 복사 → **정본 교체** | 복사가 끝나고 교체가 커밋되기 전에는 옛 정본을 건드리지 않는다 |
| delete | 유예가 지난 `dropped` 배치 | **실물 삭제 → 행 거두기** | 순서가 뒤집히면 실물이 장부 밖으로 떨어진다 |

대상이 서로소다 — observe는 pending, copy는 자리가 열린 파일, delete는
파일이 아니라 실물 주소를 가리킨다.

상태 전이만 하는 일은 여기 오지 않는다. 소프트 삭제 집행과 만료 중단은
정본을 버려짐으로 넘기는 갱신일 뿐이라 판단자가 회차 안에서 직접 한다 —
실물은 그렇게 생긴 `dropped` 배치에서 delete 갈래가 도출된다.

## 이동 — 자리를 열고, 채우고, 정본을 옮긴다

"이 파일을 저기로"는 운영자나 정책의 **결정**이라 파일 상태에서 읽어낼 수
없다. 적지 않으면 재시작 후 사라지므로 배치에 자리를 하나 연다. 그 자리가
곧 의도다 — 별도의 이동 저널이 없다 (ADR 007).

```
① 자리 열기   dest 에 staging 배치를 만든다        이 행이 의도다
② 복사        같은 object_key 로 실물을 쓴다        키가 같아 재시도가 멱등
③ 교체        staging → primary, 옛 primary →      두 갱신이 한 tx.
              dropped(유예 15분)                    어느 쪽이든 0행이면 롤백
④ 회수        유예가 지나면 옛 실물을 지우고 행을   delete 갈래가 맡는다
              거둔다
```

**강등이 승격보다 먼저다.** 파일당 정본 하나라는 제약이 매 문장 경계에서
성립해야 하기 때문이다.

- **경합 규칙**: 삭제·덮어쓰기·취소가 끼어들면 요청 경로가 이기고 이동이
  조용히 진다. 진 이동이 써 둔 실물은 staging을 버려짐으로 넘겨 정리에
  맡긴다 — 지우는 일이 이미 한 갈래로 있으므로 따로 짜지 않는다.
- **취소는 한 줄이다**: 자리를 버려짐으로 넘긴다. 복사가 이미 끝났는지 알
  필요가 없다 — 없는 실물을 지우는 것도 성공이므로 집행자가 알아서 정리한다.
- **읽기와의 공존**: 읽기는 정본을 매 요청 재해석한다 — 교체 전엔 옛 자리,
  후엔 새 자리를 보고 둘 다 실물이 있다. 교체 이전에 발급된 URL은 ④의 유예가
  덮는다.
- **스풀 예산 공유**: 복사는 요청 경로의 중계 업로드와 같은 스풀 슬롯을
  잡는다. 같은 로컬 디스크를 쓰므로 예산이 하나여야 한다.

| 동사 | 호출 | 뜻 |
|---|---|---|
| 요청 | `POST /api/admin/v1/moves/{file_id}` `{storage_id}` | 자리 열기 → 202. active·동종 kind만. 진행 중이면 409 |
| 조회 | `GET /moves` · `GET /moves/{file_id}` | 열려 있는 자리 |
| 취소 | `DELETE /moves/{file_id}` | 자리를 버린다. 교체 뒤면 409 |
| 이력 | `GET /moves/history` | 종결 원장 (moved·lost) |

다른 kind로의 이동(s3↔fs)과 5GiB 초과는 후속이다 — 키 규칙과 복사 방식이
달라진다.

## 배치 정책 — 언제 옮길지를 자동으로 정한다

정책은 배치를 **제안만** 한다. 조건에 맞는 파일의 자리를 여는 것이 전부라
바이트를 만지지 않고, 그래서 판단자의 몫이다. 운영자 요청과 완전히 같은
프리미티브를 쓴다. 여기서 규칙이 틀려도 최악은
"쓸데없는 이동"이지 데이터 손실이 아니다 — 안전은 이동 메커니즘이 진다.

정책은 **storage가 소유한다.** "이 storage가 차면 저기로 내린다"는 그
storage의 성질이지 파일이나 클라이언트의 성질이 아니다. storage 등록을
지우면 정책도 함께 사라진다.

```
압박 게이트   점유 > high%  → 켜진다.  low%에 닿으면 멈춘다 (히스테리시스)
후보 조건     min_size · min_idle_secs — 지정한 것만 AND로 걸린다
선정 순서     가장 차가운 것 먼저 (마지막 읽기, 없으면 확정 시각)
서열          같은 source에 여럿이면 priority 낮은 쪽이 먼저 고른다
```

폭주를 막는 것이 넷이다.

| 장치 | 무엇을 막나 |
|---|---|
| 히스테리시스 (low < high) | 경계에서 끝없이 오가는 것 |
| **열린 자리의 바이트를 점유에서 뺀다** | 회차를 건너 과녁을 지나치는 것 |
| dest 여유를 회차 안에서 깎는다 | 거의 찬 dest를 넘겨버리는 것 |
| 쿨다운 · 회차당 상한 | 두 정책 사이를 오가는 것 · 벤더 요청 폭주 |

두 번째가 가장 미묘하다. 이동 중인 파일은 아직 옛 자리에 있어 점유에
잡히지만 후보에서는 빠진다. 그 바이트를 빼지 않으면 매 회차가 "아직 안
줄었다"고 보고 또 생성해서, 집행이 생성을 따라가지 못하는 만큼 필요한
양의 몇 배가 쌓인다.

| 동사 | 호출 |
|---|---|
| 등록 | `POST /api/admin/v1/policies` `{source_storage_id, dest_storage_id, priority?, min_size?, min_idle_secs?, high_pct?, low_pct?}` |
| 조회 | `GET /policies` · `GET /policies/{id}` — `last_run_at`·`moves_generated` 포함 |
| 해제 | `DELETE /policies/{id}` (멱등) |

승격(차가운 곳에서 뜨거운 곳으로)은 방향이 반대일 뿐 같은 규칙이다 —
`min_idle_secs` 대신 접근 빈도를 보는 조건이 필요해지면 그때 더한다.

## 설정

| 변수 | 기본 | 축 |
|---|---|---|
| `FILEGATE_RECONCILER_INTERVAL_SECS` | 60 | 판단 주기 (클러스터 1개) |
| `FILEGATE_WORKER_CONCURRENCY` | 8 | **파드당** 집행 워커 수 |

집행 용량은 `파드수 × FILEGATE_WORKER_CONCURRENCY`다. 판단은 파드를
늘려도 하나다. 나머지(enqueue 상한·claim 만료·backoff·GC 배치)는 코드
상수다 — 운영이 만질 이유가 생기면 그때 설정으로 올린다.

## 경계선

- 큐에 드는 것은 저장소 백엔드 I/O가 있는 작업뿐이다. SQL 한 문장이 곧
  배치인 정리(보존 정리·스냅샷)는 나눌 단위가 없어 reconciler가 직접 한다.
- 우선순위는 없다 — 세 갈래가 모두 정리 작업이라 서열이 의미를 갖지
  않는다. 서열이 필요한 작업이 생기면 그때 도입한다.
